# テストの方針

TDD で進めるうえでの、テストの書き方と分け方の決めごと。

## テストサイズで考える
「単体テスト」「結合テスト」という呼び方は人によって意味がぶれるので、Google のテストサイズで考える。

- **Small**: 1つのプロセスの中で完結し、ファイルの読み込みや時間待ちを使わない。速い
- **Medium**: ファイルの読み込みや、物理エンジンの進行(物理フレームを待つ)などを使う。遅い

## 遅さの原因は物理フレームを待つこと
2026-10-02 の計測(1,000回の平均):

| 処理 | 1回あたり |
|---|---|
| `Player.new()` で作って消す | 約 0.08ms |
| シーンから `instantiate()` で作って消す | 約 0.15ms |
| シーンのファイルを読み込む(最初の1回だけ。以後はキャッシュ) | 約 5ms |
| 物理フレームを1回待つ | 約 13ms |

- シーンから作っても、`new()` との差はごくわずか。シーン化するかどうかは、テストの速さの問題ではない
- テストが遅くなるのは、視線のレイや段差の判定のために物理フレームを待つから。プレイヤーのテストは、`Player.new()` で作っていても、すでに Medium になっている

## 判断のロジックは、物理に頼らない小さな部品に切り出す
- 物理エンジンや Node に頼らない判断(どの相手を選ぶか、途中の位置の計算、待ち時間の数え方など)は、RefCounted の小さな部品に切り出して Small テストで確かめる。ドメイン層(`Lifespan`、`Attention`、`Emergence` など)と同じ形
- 物理エンジンが要る部分(視線のレイ、着く場所の確認、段差の判定など)は Node に残して薄くし、数の少ない Medium テストで「物理とつながっているか」を確かめる(Humble Object パターン)
- 自分で作っていないもの(Godot のエンジン)をモックでまねしない
- テストが遅い、書きにくいと感じたら、ロジックとフレームワークが混ざっているサインと受け取る

## 形や見た目はシーンに置く
- 当たり判定の形、カメラ、UI の配置などはシーン(.tscn)に置き、振る舞いはスクリプトに書く(docs/todo.md の「シーンへのリファクタリング」)
- 実行中に数や中身が決まるもの(群衆の NPC の出現、設計図の影、街の生成など)はスクリプトで作る

## マップのような中身のデータ
- マップはロジックではなくデータなので、テストを先に書いて作るものではない
- 街の地図(src/world/city/city_map.txt)はデータ。地図を読み解いて部品の並べ方を決めるロジック(CityPlan、CityPieces、BlockFiller)は、テストを先に書いて作る(Small)
- 焼き込んだ街のテスト(test/integration/test_city.gd)は、歩く所に穴がない、建物に当たり判定がある、街の外へ出られない、などゲームとして困ることだけを確かめる(Medium)
